# 差距清单与优先级

> 版本：2026-10-10（2026-10-14 复核更新：XLSX、反馈闭环、评测流水线已落地，并新增 §3.1 的新差距）
> 定位：对照 `知识库产品设计方案.md` 的 S0~S10 能力定义与成熟检索增强实践，逐层列出差距并给出优先级。
> 原则：判定只基于**代码里真实成立的事实**；把"真差距"和"看着像差距"分开，避免把力气用错地方。
> 读法：第 2 节是总账，第 3 节是要做的事，第 4 节是**不要动**的地方，第 6 节是顺序。

---

## 1. 结论先行

1. 检索这一层，**召回和权限已经不落后，甚至领先**：混合召回（向量 + 关键词）、RRF 融合、ACL 在 SQL 里下推、引用校验、拒答阈值标定、片段级账本。
2. 真正拖后腿的是四件事：**重排（无 cross-encoder）、查询改写（未做）、解析（启发式）、上下文增强（未做）**。
3. 其余差距大多是**产品化与规模化**，不是检索质量问题，别和上面四件混在一起排期。
4. 建议顺序：`重排 → 上下文增强 → 查询改写 → 解析`；其余按需。

## 2. 能力对照（分层总账）

| 层 | 现状（证据） | 成熟做法 | 差距 | 判定 |
|---|---|---|---|---|
| 数据接入/同步 | 内容哈希幂等、先删后传（`架构说明.md` §7） | 对齐 | 小 | 维持 |
| 文档解析 | PDFBox/POI + 启发式标题（`架构说明.md` A6） | 版面分析 + OCR + 表格 | **大** | 补 |
| 切分 | 结构切分，纯函数有单测；粒度写死 200（`parse/ChunkSplitter.java:28`） | 语义切分 + 粒度可配 + 上下文增强 | 中 | 部分补 |
| 索引 | 向量 + `pg_trgm` 双索引（`架构说明.md` §2） | 对齐 | 小 | 维持 |

| **查询改写** | P1/P2 明确不做（`retrieval/KnowledgeRetriever.java:24`） | 多查询 / HyDE | 中 | 补 |

| 规模化 | pgvector 单库 | 分布式向量库 | 暂非瓶颈 | 暂缓 |

一句话：**召回和权限你已经领先，真正拖后腿的是"重排、改写、解析、上下文增强"这四件。**

> **管理能力（2026-10-10 补）**：原来"创建知识库 / 上传文件 / 版本"都只能靠"目录 + manifest 手工登记 + 扫描"，
> 现补上服务端入口（均 admin-only）：**知识域 CRUD**（`/api/domains`）、**浏览器上传**
> （`POST /api/ingest/upload`，服务端写盘 + 自动登记 manifest + 入库）、**文档版本状态切换**
> （`PUT /api/documents/{id}/status`，现行 / 已废止 / 草案）。前端分别在「知识域管理」「文档与同步」两页。
> 规模化仍"另议"。

> **多项目接入（2026-10-14）**：让多个项目共用这一套服务时"各自的用户 / 各自的库"怎么分，
> 已定稿在 **[`多项目接入方案.md`](多项目接入方案.md)**。要点：可见性三级（私有 / 项目内公开 / 指定人·部门，
> **不做跨项目公开**）、库归属租户、三级主体（平台管理员 / 租户管理员 / 普通用户）、管理权与可见权分离。
> **S1 租户地基已实施**（`tenant`/`tenant_member` 表、域加 `tenant_code`+`created_by`、老域回填默认租户）；
> **S2 起未做**——最需要注意的两条"静默泄漏"风险仍在：`domain_acl` 里的 `ALL:*` 当前是**平台全局**语义、
> 检索链路还没有租户谓词——两者必须同批改。
> 同一批把数据库迁移切到 **Flyway**（`db/migration/V*.sql`，见 `架构说明.md` §8），并修掉了"全新空库缺 `vector`
> 扩展导致建表失败"这个既有缺陷。

## 3. 该补的（按优先级）

### P0 — 真 rerank（收益最大）

> **状态（2026-10-10）**：已落地。新增端口 `retrieval/Reranker` + 实现 `adapters/rerank/HttpReranker`（HTTP `/rerank`，
> 兼容 OpenAI/TEI 与云端 rerank 两种返回形状），在 RRF 之后、双阈值之前重排候选；配置分组「重排」控制。
> 取舍：**只改排序、不改阈值口径**（`score` 仍是余弦），开关**默认关闭**、失败 **fail-open**、3s 短超时 + 30s 熔断。
> 阈值换成重排口径的重标定仍为待办，见本文 §7.1。

- **差距**：`RrfFusion.fuse()` 的输出顺序就是最终顺序（排序键见 `RrfFusion.java:77`）。全链路没有一层负责判断"问题与片段到底像不像"。
- **为什么痛**：RRF 只看"两路各排第几"，不看语义相关性。当 top-N 里混进语义相近但答非所问的片段时，没有任何一层能把它压下去。`知识库产品设计方案.md` §4.4 S3 也把 rerank 标为"性价比最高的一步"。
- **最小补法**：在 RRF 之后、双阈值判定之前插一层 rerank（本地 `重排模型`，或云 rerank），接口做成可替换。
- **验收标志**：库外问题（应拒答）的最高分不再被抬高；60 题集里"该命中却没进 top3"的条数下降。
- **连带成本**：阈值（`ANSWER_MIN_SCORE` 等，`架构说明.md` §3）是按当前分数口径标定的；引入 rerank 后必须**重新标定**，并更新需求文档 §10.11 的记录。

### P1 — 上下文增强（Contextual Retrieval）

> **状态（2026-10-10）**：已落地（**默认关闭**）。新增 `ingest/Contextualizer` + `LlmContextualizer`，开关在「文档同步 → 片段上下文增强」；
> 入库时给每个片段补一句上下文、**随片段一起向量化**（`document_chunk.context_prefix` / `context_hash`）。
> 开启后需 `POST /ingest/reindex` 才生效；关闭时幂等指纹与旧版逐位等价，不触发全量重嵌。

- **差距**：`ingest` 包内没有任何上下文补全（无 context / summary / augment 相关实现）。
- **为什么痛**：chunk 粒度是 200 字（`ChunkSplitter.java:28`），切得细 → 召回精度高，但**片段脱离上下文后语义不完整**，rerank 和生成都会吃亏。
- **最小补法**：入库时给每个 chunk 前置一句"文档标题 > 章节路径"级的上下文摘要（用低价模型批量跑），随 chunk 一起索引。
- **验收标志**：同一批问题上，"读到了片段却答不出"的案例减少；人工抽检片段语义完整度提升。

### P1 — 查询改写（多查询 / HyDE）

> **状态（2026-10-10）**：已落地（**默认关闭**）。新增 `retrieval/QueryRewriter` + `LlmQueryRewriter`（开关 `assistant.retrieval.rewrite`）；
> 原问题 + 2~3 条变体各跑两路后**多路 RRF**（`MultiQueryFusion`）；提示词明确"型号/编号/版本号/时间范围一律原样保留"。
> 失败 fail-open 退回原问题。HyDE 未做，先落"多查询"。

- **差距**：`retrieval/KnowledgeRetriever.java:24` 白纸黑字"P1/P2 都不做查询改写"。
- **为什么痛**：用户口语化提问（"停机了怎么办"）与文档正式表述（"故障上报流程"）之间没有桥；型号/编号场景又需要反向提示"保留原词"。
- **最小补法**：低价模型生成 2~3 个改写变体，与原问题并行检索后一起进 RRF。改写提示词里明确"型号、编号、版本号、时间范围一律原样保留"（可参照 `deep/QuestionDecomposer.java:34` 的既有约定）。
- **注意**：改写不是万能药——原文没有的表述救不回来，那种情况靠深度通道的窗口扩展（`deep/EvidenceExplorer.java`）与澄清。

### P1 — 解析升级（天花板问题）

> **状态（2026-10-10）**：已到"**接缝 + 预览**"（**默认关闭**）。新增 `parse/LayoutParser` + `adapters/layout/HttpLayoutParser`
> （`POST {baseUrl}/parse` → `{blocks:[{kind,text,page,level}]}`，Docling/MinerU/PP-StructureV3 薄适配即可接入）+ 配置分组「版面分析」；
> 解析入口收敛到 `parse/DocumentParseService`（先试版面分析，失败自动回落内置 PDFBox/POI）。
> 新增**解析预览** `POST /api/ingest/parse-preview`（admin，与入库同一条解析路径，界面上可逐份确认）。
> 真实复杂排版效果依赖外部服务；内置启发式的识别率未变。OCR 未做。

- **差距**：`架构说明.md` A6 自登记"复杂排版（双栏、扫描件）识别率未验证"。
- **为什么痛**：解析错，后面全错——切分再准、rerank 再好，都是给错误文本排序。
- **最小补法**：先接一层版面分析（Docling / MinerU / PP-StructureV3），并保留"解析预览"让人确认。
- **验收标志**：扫描件、跨页表格、双栏文档的抽检正确率；三处按文档类型分别统计，而不是只看总平均。

### 3.1 P3 之后新增的差距（2026-10-14 复核）

按"影响答案质量"排序，与上面 §3 的 P0/P1 不重复：

| 项 | 现状（证据） | 为什么痛 | 最小补法 |
|---|---|---|---|
| **中文关键词通道无分词** | `DocumentChunkRepository.keywordQuery` 用 `word_similarity` + `pg_trgm`（字符级三元组，无词典） | 中文短查询（"停机怎么办"）召回明显吃亏；这是中文库最实际的短板 | BM25 + 中文分词（ParadeDB `pg_search` / zhparser / jieba），或独立 ES |
| **"命中后带相邻块"没做** | `ChunkSplitter` 类注释承诺"上下文不足放到检索阶段解决"，但检索侧没实现（只有 deep 通道做窗口扩展） | chunk 150~200 token，片段脱离上下文语义不完整 | 命中后按 `(document_id, chunk_index ± 1)` 取相邻块拼进证据（small-to-big） |
| **重排默认关闭、阈值未按重排口径重标** | `HttpReranker.enabled()` 需显式开启；`ANSWER_MIN_SCORE=0.51` 仍是 RRF 口径 | 代码已就绪但线上没吃到收益 | 开开关 + 用题集重标阈值（现在有评测器了，标定可量化） |
| **无缓存** | 查询 embedding、检索结果、prompt 全无缓存；只有钉钉 token 与查看 PDF 用了缓存 | 企业内部重复问题比例高，成本/延迟可省 | embedding 按文本哈希缓存（最稳），检索结果按 (query, domain, ACL 快照) 短 TTL |
| **无自动重试/退避，熔断只有重排一处** | `HttpSupport` 单次请求，429/5xx 直接失败 | 模型抖一下整个问答就挂 | 统一重试（指数退避+抖动）+ 每依赖熔断（复用 `HttpReranker` 的写法） |
| **多轮对话 / 指代消解缺失** | `AnswerRequest(domainCode, question, topN)` 无历史 | "它的压力是多少"这类追问无法工作 | 带 conversationId，检索前先把问题改写成独立问题 |
| **密级未参与检索过滤** | `document.secrecy` 只展示，SQL 里没有密级谓词 | 若企业要按密级过滤，目前只能靠文档级 ACL 近似 | 与 ACL 在同一处下推密级谓词 |
| **深度通道不写账本** | `deep/*` 不调用 `ObserveService`，`verify-deep.ps1` 无法按账本复核 | 深度问答的成本/命中无法统计，评测也覆盖不到 | 深度通道按同一口径写 qa_trace（或至少写 run 级汇总） |
| **PPTX 幻灯片标题在章节路径里层层嵌套** | `ChunkSplitter.levelOf()` 不看 `level` 字段：无编号的标题按"当前深度+1"处理，于是幻灯片标题串成"封面 &gt; 系统组成 &gt; 主要参数" | 每张幻灯片的片段都挂着前面几张的标题进向量，检索语义被稀释（XLSX 已用"表名带编号"绕开，PPTX 同类问题未修） | 要么让 `ChunkSplitter` 采信解析器给的 `level`（PPTX/XLSX 解析器知道"标题/表名是平级的"），要么给幻灯片标题编号——前者更根本，但要动切分 |

> 注：解析侧的**扫描件/OCR**与**版面分析**仍按 §3 的 P1 排在前面——xlsx 接入解决的是"格式覆盖"，
> 扫描件解决的是"能不能解析出文字"，两者不是一件事。

## 4. 不该动的（护住领先项）

| 项 | 为什么别动 |
|---|---|
| 混合召回 + RRF | 两路分数量纲不可比（`RrfFusion.java:11` 注释已说明）；改成加权求和等于把"米"和"公斤"相加 |

## 7. 开放问题

1. **rerank 引入后阈值要重标**：现有"应作答 0.529 / 库外 0.497"的可分区间（需求文档 §10.11）是 RRF 分数口径下的，换层会改变分布，必须重跑标定。→ **仍待办**：本次已把重排做成"只改排序、不改阈值口径"且默认关闭，故不重标也不影响现有行为；要真正把作答阈值换成重排口径，仍需先跑 60 题集标定。
2. **上下文增强的成本**：给每个 chunk 跑一次便宜模型，是入库期的一次性成本，需要评估语料规模下的耗时与费用。
3. **改写与深度的边界**：改写属于"快速通道也要更好"，容易和深度通道的拆解重叠，注意别把简单问题也拖进多轮。
4. **解析优先级**：解析是天花板，但投入最大、见效最慢——放在 P1 末位，先用真实语料证明是瓶颈再上。
5. **~~查看器与内嵌图脱节~~（2026-10-14 已修）**：图片依旧不进 chunk 正文，但**不再需要**给 `Block` 加图片字段——
   改成 sidecar：`image_asset.page`（幻灯片号）与块的 `pageFrom` 天然同源，`DocumentViewService.converted()` 取图、
