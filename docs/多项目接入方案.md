# 多项目接入方案（多租户与可见性）

> 状态：**设计已定；S1 租户地基、S2 可见性收窄、S3 租户管理员均已实施（2026-10-14），S4 起未做**
> 定位：让多个项目共用这一套知识库服务时，"各自的用户"与"各自的库"怎么分。
> 关系：本文是 `差距清单与优先级.md` 里"产品化 / 多租户"那一条的展开；与 `架构说明.md` §4 权限边界、§9 身份与对外接入直接相关。

---

## 1. 要解决的问题

别的项目想直接用这里的检索/问答/找图，但：

- **它有它的用户体系，我们有我们的**——两边的"人"对不上
- **库要分开**——A 项目的资料不能让 B 项目搜到
- **同一个人在不同项目里角色可能不同**（在 A 是管理员，在 B 只是普通成员）

---

## 2. 已确认的决策（2026-10-14）

| # | 决策 | 明确不做的 |
|---|---|---|
| 1 | **可见性分三级**：私有 / 项目内公开 / 指定人·部门 | ❌ **不做"跨项目公开"**——没有"所有租户都能看"这一级 |
| 2 | **库归属租户**（不是归个人）。创建者只是 creator，用于审计 | 不做"个人所有"的库（避免人走了库变成孤儿） |
| 3 | **三级主体**：平台管理员 / 租户管理员 / 普通用户 | 租户管理员 ≠ 发一个 admin 角色给他 |
| 4 | **权利分离**：creator 与租户管理员有**管理权**（改/删/授权）；被授权的成员只有**可见权**（检索/查看） | 不做"公开 = 大家都能改" |
| 5 | 外部项目调用默认**代表项目**（应用身份）；终端用户身份只做审计 | 本轮不做"按终端用户真判权"（留升级路径，见 §6） |

---

## 3. 概念模型

### 3.1 三级主体与权利

| 主体 | 范围 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **平台管理员** | 全部租户 | 建租户、配置系统、配置全局参数 | —— |
| **租户管理员** | **只限自己租户内**的域、成员、授权 | 在租户内建库、授权、审核上传、管成员 | 看别的租户的域与文档 |
| **普通用户** | 自己被授权的库 | 检索、问答、查看原文、（可选）上传待审核 | 管别人建的库 |
| **creator**（库创建者） | 自己创建的库 | 改、删、授权（管理权） | 管别人建的库 |

> **关键**：`creator` 是能力而不是角色——租户管理员也有它。**归属决定生死**（归租户），**creator 只用于审计与"能管自己建的库"**。

### 3.2 可见性三级 → 用现有 ACL 表表达

三级可见性**全部复用 `domain_acl`**（它已经支持 `ALL / ROLE / DEPT / USER` 四种主体、`permission` 恒 `READ`）：

| 级别 | 谁能看 | 落到 `domain_acl` | 典型场景 |
|---|---|---|---|
| **私有** | 只有本人 | `USER:<username>` | 个人草稿、在整理的材料 |
| **项目内公开** | **本租户**全员 | `ALL:*`（**语义收窄到租户内**，见 §4 坑 1） | 项目内部共享 |
| **指定人 / 部门** | 指定主体 | `USER:` / `ROLE:` / `DEPT:` | 只给质检组看 |

**可见权与管理权走两条路**，这带来一个好处：`domain_acl.permission` **仍然恒为 `READ`**，不需要为它引入新的权限类型，fail-closed 语义与"没有授权行就看不见"的既有口径**完全不变**。

管理权由两处判定，不进 `domain_acl`：

```
能管这个库 = (当前用户是该域的 created_by) 或 (当前用户是该域的租户的管理员)
```

### 3.3 一个例子走一遍

租户 A 里：张三建了库 `a`，李四建了库 `b`，王五是 A 的租户管理员；租户 B 的赵六什么都看不到。

| 人 | 能看到 | 能管 |
|---|---|---|
| 张三 | `a` | `a` |
| 李四 | `a`（张三设了项目内公开）、`b` | `b` |
| 王五（租户管理员） | A 里所有库 | A 里所有库 |
| 赵六（B 项目） | 无 | 无 |

张三把 `a` 设为"项目内公开"后：**只对租户 A 全员公开**，对 B 依然完全不可见——**"公开"的作用域永远 ≤ 所属租户**。

## 4. 现状差距与三个必须一次性做对的点

| # | 现状（证据） | 目标 | 风险 |
|---|---|---|---|
| 1 | `domain_acl` 里的 `ALL:*` **当前是"平台全局所有人"语义**（`V1__baseline_schema.sql` 的 domain_acl 段） | 收窄为**"本租户全员"** | **静默跨租户泄漏**：A 设成公开的库会出现在 B 的检索结果里，不报错、只在数据上表现出来 |
| 2 | `knowledge_domain` 只有 `code/name/description/enabled/sort_order/created_at`（`V1__baseline_schema.sql` 的 knowledge_domain 段），**没有归属列** | 加 `tenant_code` + `created_by` | 没有归属，"项目内公开"没有作用域可依附 |
| 3 | 只有全局 `admin`（`app_role` 表，`@RequireRole("admin")`），且**全局 admin 刻意"能看全部"**（为了审核草案，见 `DocumentVisibility.visibleByStatus`） | 新增**租户管理员**（受租户限制） | 把 admin 发给项目方 = 把别的项目也交出去 |
| 4 | 域 CRUD 与域授权是 **admin-only**（`DomainController:45,52`、`AdminDomainAclController:27`） | 放开到租户管理员 | 项目方无法自助建库 |
| 5 | ACL 在 **SQL 里下推**（`AccessFilter` + 三条 chunk 查询 + 找图 + 查看 + 列表） | 每条查询再加一层**租户谓词** | **这是最不能漏的一条**：漏一条就是静默跨租户泄漏，且性能上要走索引 |

> 第 1 条与第 5 条是"不报错的错"，比报错危险得多——它们必须是同一批改动，不能分两次上。

> **S1 已实施（2026-10-14）**：`tenant` / `tenant_member` 两张表、`knowledge_domain.tenant_code`（NOT NULL，
> 升级前就存在的域已回填 `default`）与 `created_by` 都已落地；建域时可指定租户、创建者自动记录；
> 管理端「知识域管理」多了租户列。**表里的第 1、3、4、5 条仍未做（S2/S3）**——也就是说
> "静默跨租户泄漏"的风险目前依然存在，只是结构先备好了。同一批还把数据库迁移切到了 Flyway（见 `架构说明.md` §8）。

## 5. 目标数据模型（最小改动）

```sql
-- 租户本体（平台管理员"建租户"需要一个落点）
create table if not exists tenant (
    code        varchar(32) primary key,
    name        varchar(64) not null,
    description text,
    enabled     boolean     not null default true,
    created_at  timestamptz not null default now()
);

-- 库的归属与创建者（归属决定生死，创建者只用于审计与"管自己建的"）
alter table knowledge_domain add column if not exists tenant_code varchar(32) references tenant(code);
alter table knowledge_domain add column if not exists created_by  varchar(64);

-- 人属于哪些租户、在租户里是什么角色
create table if not exists tenant_member (
    id          bigserial primary key,
    tenant_code varchar(32) not null references tenant(code) on delete cascade,
    user_id     bigint      not null references app_user(id) on delete cascade,
    role        varchar(16) not null,   -- admin（租户管理员）/ member（普通成员）
    created_at  timestamptz not null default now(),
    unique (tenant_code, user_id)
);
```

### 5.1 为什么是 `tenant_member` 表，而不是给 `app_user` 加一列

`app_user.role_code` 是**全局单角色**（`V1__baseline_schema.sql` 的 app_user 段）。而你的场景里就存在"**同一个人在 A 项目是管理员、在 B 项目只是普通成员**"——一列表达不了。用 `tenant_member` 一对多，天然支持一个人属于多个租户、在不同租户里角色不同。这也是本文档里唯一一处"新表"，其余全是加列。

## 6. 外部项目怎么接（两种口径，本轮只做第一种）

### 6.1 本轮：代表项目（应用身份）——零改代码就能用

```
外部项目  ── API Key（绑该项目的服务账号）──▶  本服务
```

- 每项目一把 Key，绑 `service` 角色的账号（`app_role` 里已有这个角色，注释写的就是"供外部 API Key 绑定的非交互账号"）
- 把该租户的域授权给这个服务账号；**项目内部"谁能问"由对方系统自己判**
- 我们能审计到"哪个项目"，**审计不到具体是谁**

### 6.2 升级路径（本轮不做，留好接口）

外部项目在请求里带终端用户标识（弱断言，例如 `X-End-User`），我们把它**只写进账本**、不用于判权——这正是 Dify 的 `user` 参数用法。

要真正"按终端用户判权"时，再把弱断言换成签名令牌，**判权位置不用重写**（主体早就在账本里了）。这也是我们相对 Dify 的差异位：

| 能力 | Dify / 多数平台 | 本系统 |
|---|---|---|
| 租户/工作区硬边界 | ✅ | 目标（本文档） |
| 应用级 Key | ✅ 绑应用 | 目标：绑租户/域（现在绑账号，见差距清单） |
| 终端用户身份 | 只做会话与统计，**不判权** | 同上（先弱断言） |
| **按终端用户做文档级判权** | ❌ 原生没有（要靠应用自己传 metadata filter，等于判权移回调用方） | ✅ **有 ACL 下推，可以真判权** |

## 8. 明确不在本轮范围

- **跨项目公开**（平台级公开）：已确认不需要。若将来要，需要额外设计"谁能把库提升为跨项目公开"（应由平台管理员审批，而不是项目自己说公开就公开）
- **多租户 SaaS 化**：计费、配额、租户级限流不在本轮
- **跨租户共享语料**：不做。租户之间是硬边界
- **按终端用户真判权**：留升级路径，见 §6.2

## 9. 与既有设计的关系（哪些别动）

- **别动"权限在 SQL 里下推"**：租户谓词是同一条路子加一层，不是改成"查完再过滤"——改成事后过滤会把不该看的内容泄漏进日志、缓存与引用链接
- **别把 `domain_acl.permission` 扩成读写**：可见权与管理权分离（§3.2），管理权走 `created_by` + 租户管理员
- **别把租户管理员实现成"发一个 admin 角色"**：全局 admin 能看全部，是多租户下最危险的授权
- **别用命名约定代替 `tenant_code`**（如域 code 加前缀）：约定不是约束，迟早有人不遵守，而失败方式是静默泄漏
