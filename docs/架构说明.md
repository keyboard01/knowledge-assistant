# 架构说明

> 适用版本：2026-10-13（身份/权限地基 + 对外接入）
> 本文只写**代码里真实成立**的结构，不写计划中的结构。与实现的偏离统一记在第 11 节。

---

## 1. 分层与依赖方向

```text
前端 (Vue 3 + Vite，两个独立入口：index.html 用户门户 / admin.html 管理控制台)
   │  /api/**（Bearer 会话令牌；外部系统用 API Key）
   ▼
web 层（各 *Controller）
   │  只依赖同包 Service；身份一律从 CurrentUser（服务端推出）取，不接受前端传
   ▼
service 层
   ├─ security/   登录、会话、API Key、角色、域级+文档级 ACL 与过滤条件生成、钉钉 SSO 与组织同步
   ├─ ingest/     目录扫描、幂等同步、重试、自建 chunk 落库、用户上传（审核默认草案）
   ├─ parse/      DocumentParseService：先试版面分析（可选）否则内置 PDFBox/POI → 块 → chunk（页码、章节路径）
   ├─ retrieval/  召回编排、权限过滤、融合、证据组装、双阈值
   ├─ generation/ 证据编号、提示词组装、引用校验、拒答判定
   ├─ observe/    运行记录账本（qa_trace / qa_trace_evidence）
   ├─ media/      找图：图片抽取（PDF/DOCX/直传）、VLM 描述、内容寻址落盘、图片检索（复用 security 的权限栈）
   ├─ mcp/        MCP Streamable HTTP：JSON-RPC 2.0 分发 + 四工具（复用 retrieval/domain/view/media 服务）
   └─ view/       文档查看：ACL 复核 + 审计（document_view_log）、Markdown 拼装、PDF 盖章、DOCX→PDF 重排
   ▼
adapters/        HTTP 出口：embedding、llm、vision（图片理解）、imageembedding（视觉向量）、rerank、layout、dingtalk
   ▼
PostgreSQL 17 + pgvector（元数据 / 域级+文档级 ACL / chunk / 自建向量 / 图片资产 / 账本 / 会话 / API Key）
磁盘            文档根 `sourceRoot` + 图片资产根 `assetRoot`（内容寻址，`{sha[0:2]}/{sha[2:4]}/{sha}.{ext}`）
```

**唯一身份入口**是 `security/AuthInterceptor.preHandle`：它把"会话令牌 **或** 对外 API Key"解析成一个
`AppUser`，写入 `CurrentUser`，再执行 `@RequireRole`。因此接入新身份（服务账号、钉钉免登）**不需要动
`AccessFilter` 与任何控制器**——它们只读 `username` / `roleCode` / `deptCode`。

## 2. 三类数据，各自归属

| 数据 | 存在哪 | 谁写入 | 用途 |
|---|---|---|---|
| 文档元数据 + ACL | `document` / `document_acl` | `ingest` + manifest 登记表 | 权限判定、版本并列、目录展示 |
| 域级授权 | `domain_acl` | admin（工作区授权页）；新建域默认写 `ALL:*` | 工作区可见性（权限的第一级门，fail-closed） |
| 自建 chunk（正文 + 页码 + 章节路径 + 向量） | `document_chunk`（`embedding vector(1024)`、`content` 上有 `pg_trgm` GIN 索引） | `parse` + `chunkIndexer` | **P2 起的主要检索来源**：向量召回 + 关键词召回 |
| 连接与模型配置 | `app_setting` | admin | 向量化、生成、重排、版面、钉钉、图片理解、视觉向量 |
| 运行记录 | `qa_trace` / `qa_trace_evidence` | `observe` | 拒答率、耗时、token 与费用、片段级是否被引用 |
| 图片资产 | `image_asset`（`embedding vector(1024)`、`search_text` 上有 `pg_trgm` GIN） | `media`（`MediaIndexer`） | 找图：向量 + 关键词召回 `caption + ocr`；权限靠 `document_id` 复用文档 ACL |

**片段天然带着 `document_id`**，反查本地文档行不需要任何外部键。`RetrievalDiagnostics` 里的
`kernelTopN/kernelHits` 是历史命名，实际含义是"送进检索的候选上限/命中总数"。
| 账号 / 会话 / 外部身份 / 对外密钥 | `app_user`（含 `external_source`/`external_id`）/ `app_session` / `api_client` | `security` | 登录身份、钉钉映射、对外 API Key 绑定 |
| 连接与模型配置 | `app_setting` | admin | 向量化、生成、重排、版面、钉钉、图片理解、视觉向量 |

**为什么要自己再存一份向量**：外部检索通道既拿不到页码与章节路径，也给不出可解释的名次。要页码级引用、要
"两路各排第几"的定责信息，就必须自己掌握 chunk 与向量（这是 D1 的边界决定的，不是重复建设）。

## 3. 检索链路（P2）

```text
问题
  ├─（可选，默认关闭）查询改写：产出 2~3 条变体，与原问题一起召回；每条各跑下面两路
  ├─ 向量通道：document_chunk.embedding 余弦相似度（HNSW 索引）
  └─ 关键词通道：word_similarity(content, 问题) ≥ 0.12（pg_trgm GIN 索引）
        │  两条通道的 SQL 都**内联 ACL 过滤**（在权限可见范围内召回）
        ▼
     多路 RRF 融合（k=60）+ 精确词半票 →（可选，默认关闭）cross-encoder 重排 → 取 topN
        ▼
     按文档聚合 → 版本并列与冲突标记 → 双阈值判"证据是否足够"
        ▼
     Evidence（带 chunkId / 页码 / 章节路径 / 两路名次）
```

**双阈值语义**（`retrieval/RetrievalService`、`retrieval/RrfFusion`、`retrieval/LocalChunkRetriever`）：

| 常量 | 值 | 含义 |
|---|---|---|
| `DEFAULT_MIN_SCORE` | 0.25 | 召回下限：低于它的片段连候选都不进（宽） |
| `ANSWER_MIN_SCORE` | 0.51 | 向量作答下限：最强片段低于它，就不能只靠向量作答（严） |
| `ANSWER_KEYWORD_SIMILARITY` | 0.42 | 关键词作答下限（**两路任一达标即可作答**） |
| `KEYWORD_MIN_SCORE` | 0.12 | 关键词召回下限 |
| `RrfFusion.DEFAULT_K` | 60 | RRF 融合常数 |

这些是**编译期常量，不是配置项**。标定依据见需求文档 §10.11（应作答最低分 0.529 vs 库外最高分 0.497，
可分区间只有 (0.497, 0.529)）。把它们做成配置项的风险大于收益：改一次阈值就能让"该答的拒答"和
"不该答的硬答"同时发生，而且从账本上看不出是谁改的。

**检索通道**：只有自建一条（混合召回 + RRF + 可选重排）；早期的 AnythingLLM 内核通道已于 2026-10-13 移除。

**查询改写（P1，默认关闭）**：开关 `assistant.retrieval.rewrite`（默认 `off`）。开启后用生成模型产出
2~3 条更接近文档说法的变体（型号/编号/版本/时间范围原样保留），**原问题与变体各跑向量与关键词两路**，
再进多路 RRF（`MultiQueryFusion`：每条通道各贡献 `1/(k+rank)`，精确词半票只加一次）。
关闭时只跑原问题、走两路 `RrfFusion.fuse`，与引入改写前**逐位一致**。任何失败 fail-open 退回原问题。

**重排（rerank，P0，默认关闭）**：RRF 只看"两路各排第几"，不看"问题与片段到底像不像"。
在 RRF 之后、双阈值之前插一层 cross-encoder（端口 `retrieval/Reranker`，实现
`adapters/rerank/HttpReranker` → `RerankClient`），按 `rerankScore` 重排候选。它**只改排序、不改阈值口径**：

- `RetrievedPassage.score` 仍是向量余弦，`ANSWER_MIN_SCORE` / `KEYWORD_MIN_SCORE` 双阈值一字不动；
- 重排分单独落在 `RetrievedPassage.rerankScore`，`EvidenceAssembler` 用它排文档（缺失则回落余弦），
  但 `bestScore` 取的是"全局最强余弦"，与排序无关——否则重排换掉第一名会**间接**挪动作答阈值；
- 开关在「系统配置 → 重排」分组（`enabled` 默认 false）。未配置或调用失败一律 **fail-open** 退回 RRF 原序，
  并带 **3s 短超时 + 30s 熔断**：深度通道一次会话约 10 次检索，不能让一个挂掉的重排服务吃穿 `DeepBudget` 的耗时预算。

把阈值也换成重排口径是独立动作，需先重跑 60 题标定（见 `差距清单与优先级.md` §7.1），本次不做。

## 4. 权限边界

**可见范围只能由服务端按登录身份推出**，请求体里没有 user、没有可见范围字段——前端传什么都不影响过滤条件。

**两道门，依次过**：

1. **域级（工作区）授权** `domain_acl`（同构于 `document_acl`，subject_type = ALL/ROLE/DEPT/USER）。判定在
   `domain/DomainService.canAccess/requireAccessible`：`admin` 短路放行，其余按规则命中。fail-closed——
   一条规则都没有 = 只有管理员可见；新建域默认写 `ALL:*`（"公开域"），管理员撤销后即为私有。
   **强制点**：域列表、检索入口（`RetrievalService.search`）、查看原文（`DocumentViewService.authorize`）、上传。
   因为每次检索只针对**一个** `domain_code`，这里用服务边界检查而不是把它内联进检索 SQL——两者等效且更省。
2. **文档级 ACL** `document_acl`（下同）。只在通过域级门之后再判。

过滤条件生成在 `security/AccessFilter`，规则是 fail-closed：

```sql
exists (select 1 from document_acl a
         where a.document_id = d.id and upper(a.permission) = 'READ'
           and ((upper(a.subject_type)='ALL'  and (a.subject_value='*' or a.subject_value=''))
             or (upper(a.subject_type)='ROLE' and a.subject_value = ?)
             or (upper(a.subject_type)='USER' and a.subject_value = ?)))
```

不写 ACL 行的文档 = 谁都看不到。这条 SQL 两个地方各用一次：

1. **检索前下推**：两条召回通道的 SQL 都内联它，无权限的片段根本不出现在候选里；
2. **检索后复核**：`retrieval/EvidenceAssembler` 再按文档 ID 过一遍 `aclByDocumentId`，并统计
   `droppedUnauthorized`（账本里能看到"本次有多少条是被权限挡下的"）。

引用片段是**随答案一次性返回**的（`GeneratedAnswer.evidences`），没有"按 chunk id 再去取一次"的接口，
所以不存在"权限撤销后旧链接仍能打开"的路径——P1 设计里的第三处复核因此不需要单独实现。

**账本比文档更严**：`observe` 整个控制器 `@RequireRole("admin")`，因为账本里是所有人的提问原话，
它本身比被提问的文档更敏感。

### 4.1 状态门：只有「现行」参与检索

`security/DocumentVisibility` 是唯一的口径来源（`CURRENT = "现行"`、`currentSql(alias)`、`isCurrent(status)`），
所有"能不能看到内容"的入口都引用它，避免"列表看得到、检索搜不到"漂移：

- **下推**：三条检索 SQL（`DocumentChunkRepository` 的 vector / keyword / blocked）都加 `d.doc_status like '%现行%'`；
- **复核**：`DocumentRef.searchable()` = `INDEXED && isCurrent`；
- **按 id 读**：深度通道 `RetrievalTools.visible()`、查看 `DocumentViewService.authorize()` 同样要求现行；
- **刻意不 gate 的地方**：`GET /api/documents`（列表）要能让管理员看到待审草案；对非管理员则收窄为
  "现行 + **自己上传的**草案"（`DocumentRepository.findVisible` 按身份分流）。

草案/废止因此**既进不了证据、也打不开原文**；审核通过（转"现行"）立即可检索——`updateStatus` 不动
`index_status`，无需重建。

## 5. 生成闸门只有一个

`/api/generation/answer` 与 `/api/generation/answer/stream` 共用 `GenerationService` + `AnswerComposer`：

- 证据不足 → **不调用模型**，直接按原因码拒答（省 token，且拒绝理由可统计）；
- 模型输出 → 引用编号越界校验（`CitationCheck`）→ 越界或截断按拒答处理，不回半句话；
- 流式只改变"何时上屏"，判定标准一字不放：`verdict` 事件才是结论，之前的正文都算未校验。

拒答（知识库里没有）与 503（模型/向量化坏了）分开报：混成同一个 200，用户会把系统故障当成"我们没这个制度"。

---

## 6. 可观测：账本要能查、能算钱

`qa_trace` 一次问答一行，`qa_trace_evidence` 记片段级明细（含 `cited`）。三个刻意的设计：

- **单价随账本快照**：当时用的单价一起写进行里，改价之后历史账仍是历史账；
- **`0 元` 与"不知道"分开**：没配单价写 `null`（界面显示"未计费"），不写 0；
- **存"当时真正下推的过滤条件"**（`RetrievalDiagnostics.accessFilter` 原文），不是"现在重推一遍应该是什么"；
- 写账失败不能让问答失败：`recordTrace` 吞异常只记日志。

## 7. 幂等与重试

- **同步幂等键**= 内容 SHA-256（同一 docNo+version 且内容未变即跳过）；
- **内容变更先删后传**，任何时刻不留两份内容（宁可短暂缺索引，可重试）；
- **自建 chunk 解析幂等**：指纹是 `content_hash:context_hash`（上下文增强关闭时后半段为空，与旧指纹等价），
  没变时重跑不增行、id 不变（`verify-parse.ps1` 的 AC-P2-002 验的就是这条）；
  `force=true` 才重算，但**重算也按 `(document_id, chunk_index)` 覆盖写**（`upsert`），不删整份重灌——
  所以 id 也不会换，账本里指向片段的引用不会因为一次重解析集体悬空（`verify-parse.ps1` 的 A3 两条断言）。
  片段变少时只删尾部（`deleteFrom`）。

**入库侧上下文增强（P1，默认关闭）**：`文档同步.contextual` 打开时，`ChunkIndexer` 用 `LlmContextualizer`
给每个片段补一句上下文摘要，**随片段一起向量化**（`document_chunk.context_prefix` / `context_hash` 两列；
展示与关键词仍用正文）。分组粒度 200 字切得细，脱离原文后语义不完整——这句摘要就是补回来的上下文。
开启后需重建片段（`POST /ingest/reindex`）才生效；关闭时两列为空，指纹与引入该能力前逐位等价。

## 8. 部署形态

单机、单租户、全 127.0.0.1：PostgreSQL 一个 Docker 容器，后端本机 JVM，前端 Vite（两个入口）。
命令与排障见 `docs/部署与启动.md`。表结构由 `db/schema.sql` 幂等执行，不用手工建表、也没有迁移工具
（离线环境的取舍：不引 Flyway，改表靠 `alter table ... if not exists` 追加）。**一次性数据迁移**（如给既有域补
默认授权）靠 `schema_migration` 标记表保证只跑一次——否则 `mode=always` 的每次启动都会把管理员刻意
撤销的授权重新补上。

**管理入口（P1）**：知识域（新建/改名/停用/删除）与文档（浏览器上传、现行↔废止切换）都走 **admin-only**
接口在界面上维护。上传沿用「目录 + manifest 登记」链路，只是把"放文件 + 写登记"两步搬到服务端
（`IngestService.upload` + `ManifestWriter`，原子写、按 `(docNo, version)` 去重）。**删除知识域时有文档则拒绝**，
且域下有文档时拒绝删除（先清理或改为停用）。文档没有删除接口——只支持状态切换（停用/废止）。

## 9. 身份与对外接入（P4）

### 9.1 端分离与角色

- **两个入口**：用户门户 `index.html`（问答 + 文档 + 上传）、管理控制台 `admin.html`（域/文档/用户/授权/运行记录/系统配置/对外接入）。同一后端、同一登录令牌；控制台在加载时校验 `roleCode==='admin'`。
- **角色**：`admin` / `hr` / `ops` / `viewer` / `service`（字典行 `app_role`，前端下拉据此生成）。
- **用户管理**：`/api/admin/users`（建号、改角色/部门、停用、重置密码）。两条硬规则：不能停用或降级**最后一个**启用管理员；停用或重置密码即作废该账号全部会话。

### 9.2 对外 API Key

- `api_client` 表绑定 `app_user.id`；密钥复用 `SessionToken`（256 位随机 + SHA-256），明文只在创建响应出现一次。
- `AuthInterceptor` 解析顺序：**先会话、失败后 API Key**；且 **API Key 不适用于 `/api/auth/**`**——否则改密码会把凭据当作"当前 token"，误删该账号全部会话。任何表缺失/异常都降级成 401，绝不 500。
- 权限完全复用 `AccessFilter`：Key 只回答"你是谁"，可见范围仍由绑定账号的角色/部门决定。对外**不新增 REST 端点**，直接用现有只读接口。

### 9.3 MCP（Streamable HTTP）

- `POST /api/mcp`，手写 JSON-RPC 2.0（离线仓库拉不到官方 SDK）。分发器 `McpJsonRpc` 是**纯类**（无 Spring/DB），协议的形状（id 回显、错误码、通知不响应）由单测钉死。
- 四工具 `search_documents` / `list_domains` / `read_document` / `search_images` 全走既有服务、用 `CurrentUser` 身份——**MCP 不是第二条权限路径**。
- 两个易错点：**通知返回 202 空体**（不是 `{}`）；**错误全部在控制器内格式化**，不能漏到 Spring 的 ProblemDetail。工具执行失败是 `isError:true` 的结果（HTTP 200），不是协议错误。

### 9.4 钉钉（组织同步 + 内免登，配置留空即禁用）

- **配置门** `security/DingTalkConfig`：`usable()` = 开关打开且 appKey/appSecret 齐全；未启用时**不做任何网络调用**，`/enabled` 回 false，同步接口直接报"未配置"。
- **出站适配器** `adapters/dingtalk/DingTalkClient`：直连 `oapi.dingtalk.com`（token 走 URL query，因为 `HttpSupport` 只支持 Bearer）；**每个响应都要查 `errcode`**（topapi 出错时 HTTP 仍是 200）；token 走内存缓存 + 失效重试，不落库、不打日志。
- **组织同步** `security/OrgSyncService` + 纯函数 `OrgSyncPlan`：按 `(external_source='dingtalk', external_id=userid)` upsert；**永不给 admin**；用户名确定性生成为 `dt_<id>`；撞本地账号名跳过；部门/用户数有上限，超限即截断。
- **内免登**：`authCode → topapi/v2/user/getuserinfo → userid → getUser → upsert → issueSession`。会话签发抽成 `AuthService.issueSession`，登录与 SSO 共用（都做"清理过期会话 + 更新最近登录时间"）。
- `app_user.password_hash` 可空：同步账号**无密码**、不能走密码登录（`findPasswordHash` 已改为对 null 安全返回）。

## 10. 找图（图片素材 / 多模态检索）

**目标**：用一句描述找到知识域里的图片（文档内嵌图 + 直接上传的图片）。**不**把图片混进问答证据——
那会动引用与拒答口径。

```text
文档（PDF/DOCX）─ 抽取 ImageExtractor ─┐
直接上传的图片 ────────────────────────┼─ 降采样 → VLM(caption+ocr) → search_text
                                       └─ 落盘 AssetStore（内容寻址）→ 文本 embedding(1024) → image_asset
```

- **图片来源**：PDF 内嵌图（PDFBox 2.x，**递归 Form XObject**、按 COS 对象身份去重、跳过 Mask/Stencil）、
  DOCX（`XWPFDocument.getAllPictures()`）、PPTX（XSLF，按幻灯片遍历图片形状，`page`=幻灯片序号）、
  直接上传的图片；后三者只留光栅格式（跳过 EMF/WMF 等无头 JVM 解不了的）。
- **图片文档**：`document.kind='image'` —— 不产 chunk，`index_status/chunk_status` 记 `SKIPPED`，
  只产图片资产。这样**复用整套 ACL / 状态 / 审核**，而不必另建一套文档概念；代价是凡按 PDF/DOCX 处理的路径
  都要按 kind 分支（查看三入口对图片文档返回 400，解析预览同理）。
- **描述**：一次 VLM 调用同时拿 caption 与图内文字（`adapters/vision`，OpenAI 兼容 content 数组带 `image_url`）；
  先降采样再 base64，省带宽与成本。
- **向量**：默认复用**文本 embedding** 对 `caption + ocr` 编码——图与查询落在同一向量空间，
  中文效果远好于没有中文文本塔的 CLIP。**代价**：纯视觉、描述里没提到的特征搜不到。
  可选启用 `image_embedding`（多模态模型，如 `qwen2.5-vl-embedding`，默认 1024 维）：图片由该模型编码进
  `vision_embedding`，查询文本也由**同一模型**编码，作为**第三路召回**与文本向量、关键词一起 RRF——这才补上"纯视觉"。
- **落盘**：内容寻址 `{assetRoot}/{sha[0:2]}/{sha[2:4]}/{sha}.{ext}`（+ `.thumb.jpg`）：跨文档、跨重传去重，
  同一张图只存一份、只描述一次。`assetRoot` 不得位于 `sourceRoot` 内（否则目录扫描会误处理）；孤儿文件不清理。
- **幂等**：`(document_id, asset_index)` upsert + 尾删；`content_hash:embed_model` 未变则该图**跳过 VLM 与 embedding**
  （VLM 才是这条链路里最贵的）。
- **失败隔离**：图片链路失败只标 `asset_status='FAILED'`，**绝不让文档入库失败**。
- **检索与查看**：与文本同一套权限——域级门 + 文档级 ACL + 「现行」状态，全部在 SQL 里下推；
  图片字节服务复用 `DocumentViewService.assertVisible`（审计 `Channel.IMAGE`）。
- **对外**：`POST /api/media/search` + MCP 工具 `search_images`；用户门户「找图」页。

## 12. 深度通道（P3a：S5 拆解 / S6 工具循环 / S7 退出 / S8 分步作答）

快速问答是"一次检索 + 一次生成"；深度通道换掉的是**取证据的方式**：拆解 → 多轮取证据 → 分步作答。
它不改 §5 的闸门——每段答案照旧要过同一个 `AnswerComposer` 与引用校验，能反查回片段才算数。

```text
问题
  └─ S5 QuestionDecomposer  拆成 ≤4 条可单独检索的子问题（只拆一轮；解析失败退化为"单子问题 = 原问题"）
        ▼
     S6 EvidenceExplorer   ① 每个子问题各检索一次（走 §3 的同一条链路，权限照旧在 SQL 里下推）
                           ② 围绕"锚点"补一个窗口：锚点 = 该子问题最强文档里已读到的最远片段，
                              窗口 = [锚点-4, 锚点+4] 共 9 段——表行是兄弟片段，只往后读会漏掉锚点之前的行
                           ③ 模型自选动作：search / read_document / finish（一轮一个，查询与片段都去重）
        ▼
     S7 GapJudge          证据齐 → 作答；有子问题没覆盖 → 先答能答的；一条证据都没有 → 澄清或拒答
        ▼
     S8 StepwiseAnswerer  子问题 ≥2 时按子问题分段生成，每段独立走 AnswerComposer（不再整段拒答）
```

| 边界 | 落在哪 | 为什么 |
|---|---|---|
| 身份与可见范围 | `RetrievalTools` **每次请求新建**，身份是构造参数而不是方法参数 | 模型连一个"能填身份"的入口都没有：越权在类型上就传不进来 |
| 预算 | `DeepBudget`（上限）+ `DeepLedger`（流水账） | 子问题 ≤4、工具调用 ≤10、轮数 ≤3、耗时 ≤120s、输出 token ≤12000；请求**只能调低**，超上限按上限算 |
| 可取消 | `DeepRunRegistry` + `POST /api/deep/cancel` | 取消是"在下个步骤边界停下"，不是掐断在途请求；被取消不抛 500 |
| 澄清的时机 | `GapJudge` 把澄清排在**查证据之后** | 模型判"缺限定"依据的只是问法本身，而限定条件常常就写在知识库里（住宿标准按城市分档） |

**深度通道不新增权限判定路径**：`/api/deep/**` 与 `/api/generation/**` 共用 `CurrentUser` 与
`AccessFilter`，`read_document` 的判权限逻辑与检索用的是同一份 ACL（文档不存在与"没权限"返回同一个空结果，
否则"读得到空"与"读不到"的区别本身就是一条信息）。

`DeepController` 用**独立线程池**（4 线程）：一次深度分析要占几十秒，共用池会让长任务把快速问答的线程挤干；
SSE 连接给 10 分钟超时，因为多轮探索本来就慢。

本切片实施中的偏离记在需求文档 §15.4（例如"深度运行还没进 `qa_trace` 账本"），收口时再并进 §9。
